## Hexagonal Architecture Rules (For Edge/Cloud Modules)
1. **Domain Layer (`domain` package):**
   - Core business logic resides here.
   - PRAGMATIC EXCEPTION: You are ALLOWED to use Spring Dependency Injection annotations (e.g., `@Service`, `@Component`) on domain services to avoid manual `@Bean` configuration.
   - STRICTLY PROHIBITED IN DOMAIN: Web/API annotations (e.g., `@RestController`, `@RequestMapping`) and Database/JPA annotations (e.g., `@Entity`, `@Table`, `@Column`).
2. **Application Layer (`application` package):** - Orchestrates domain objects and handles transactions.
3. **Infrastructure Layer (`infrastructure` package):** - Contains all external Adapters (PostgreSQL entities/repositories, REST Controllers, MQTT clients) and external API configurations.

## Architectural & Development Approach
- **Modular Monolith:** Both Edge and Cloud applications must be structured as Modular Monoliths. Strictly separate business domains into distinct top-level packages (e.g., `com.mes.edge.production`, `com.mes.edge.quality`, `com.mes.edge.logistics`). Whether to layer a **Microkernel/plug-in architecture** on top of this (e.g., for Edge machine-protocol adapters or OTA-friendly extension points) is a separate, not-yet-decided question — see [ADR-0003](docs/adr/0003-microkernel-architecture-consideration.md). Do not introduce plug-in loading/classloading machinery until that ADR is `Accepted`.
- **Module Isolation:** Cross-module communication must happen via public interfaces (Facades) or Domain Events. A domain in one module CANNOT directly access the database repository of another module.
- **Domain-Driven Design (DDD):** Follow DDD principles and good practices throughout the Domain layer: ubiquitous language matching the real business vocabulary (Process Engineer, Operator, Recipe, Scrap, etc. — not generic CRUD terms), Aggregates that enforce their own invariants rather than exposing raw setters, Value Objects for concepts without identity, Domain Services only for logic that doesn't naturally belong to a single Entity/Aggregate, Domain Events for significant state changes, and each vertical-slice module (`production`, `quality`, `logistics`, ...) treated as its own Bounded Context with an explicit boundary (this is what Module Isolation above already enforces technically).
  - **Known Domain Archetypes / Analysis Patterns:** When modeling a new domain concept, consider whether an established, reusable domain archetype (e.g., Fowler-style Analysis Patterns such as *Party* for people/organizations/roles, *Product*/*Product Type* for catalog-like concepts, *Quantity*, *Rule Engine*/*Specification* for encoding business rules as data) fits it before designing from scratch. These are a starting point, not a mandate — explicitly verify the fit against MES's actual rules for that concept, and if an archetype doesn't fit, say so and model it directly rather than force-fitting it. Per the "Never Assume" rule below, note which archetype (if any) was considered for a given concept and why it was used or rejected, rather than silently picking one.
- **Vertical Slicing (Feature by Feature):** Develop the system one complete vertical slice at a time (e.g., Domain -> App -> Infra -> Tests for "Operation Flow", then move to "Quality Control").
- **Incremental Shared Kernel:** DO NOT build the entire `shared-kernel` upfront. Add DTOs, Value Objects, and Domain Events to the shared kernel incrementally ONLY when a new vertical slice requires them to communicate between Edge, Cloud, or different modules.
- **Design for Testability:** At every architecture-design and implementation step, explicitly answer "how will this be tested?" — including end-to-end, not just unit/integration — as part of the design itself, not discovered afterward. If a design makes end-to-end testing hard or unclear (e.g., a hard dependency on real hardware, a real MQTT broker, or an external system with no fake/test-double seam), treat that as a design flaw to fix now (a testable seam, a fake/adapter, Testcontainers, or the Simulator module's role for exactly this purpose) rather than something to discover once `PLAN.md` Phase 15 (E2E Testing) arrives. This is the design-time counterpart to TDD below.
- **Contract Testing for Service Boundaries:** Every REST boundary between separately deployable parts of the system (Edge↔Cloud sync, Cloud's user-management API, Frontend↔Cloud API) MUST have contract tests — verifying a consumer's actual expectations against the provider, not just each side's own unit/integration tests — so a breaking API change is caught in CI rather than at E2E or in production. Which tool to use (e.g., Pact) is not yet decided — see [ADR-0005](docs/adr/0005-contract-testing-tooling.md). Do not adopt a specific contract-testing framework until ADR-0005 is `Accepted`, but treat each new cross-boundary DTO/controller as needing one once it is.
- **Test-Driven Development (TDD) — MANDATORY for every task/step:**
  1. Write the test(s) for the behavior first (unit test for Domain logic, integration test for Infrastructure adapters, etc.), before writing any production code.
  2. Run the test suite and confirm the new test(s) FAIL (red) — this proves the test actually exercises the intended behavior.
  3. Write the minimum production code needed to make the test(s) PASS (green).
  4. Refactor if needed, keeping tests green.
  - Do not write production code for a step before its corresponding test exists and has been confirmed red.
- **Architecture Decision Records (ADR):** Significant, cross-cutting, or hard-to-reverse architectural decisions (e.g., authentication/authorization mechanism, messaging patterns, storage strategy) MUST be recorded as an ADR in `docs/adr/` before implementation starts — see `docs/adr/README.md` for the process and template. Do not start implementing a `PLAN.md` step that depends on such a decision while its ADR is still `Status: Proposed`.
- **No Single Point of Assumption Failure:** Never let the overall architecture (or a large part of it) hinge entirely on one unverified technical detail or unstated assumption (e.g., "the MQTT broker is always reachable," "this library behaves a certain way," "a machine protocol supports X"). For any assumption a design is actually relying on: (1) state it explicitly rather than leaving it implicit, (2) verify it as early as possible — a spike, a quick test, a docs/vendor check — rather than building on it unverified (this is the same instinct as Shift Left, below), and (3) prefer designs where being wrong about one assumption degrades gracefully or requires a contained, local fix, over designs that would require a wholesale redesign if that one detail turns out false. If the current design depends critically on something unverified, say so rather than proceeding silently — per Never Assume, below.
- **No Exceptions for Expected Business Outcomes:** Do not use Java exceptions to represent normal, expected business results (e.g., "not found", a failed validation, an invalid state transition) — reserve exceptions for truly exceptional, unrecoverable, or programmer-error conditions (infra failures, bugs). The concrete mechanism for expected outcomes (e.g., an `Either`/`Result` type, or another approach) is not yet decided — see [ADR-0002](docs/adr/0002-error-handling-for-expected-business-outcomes.md). Do not implement Domain ports whose contracts depend on this decision until ADR-0002 is `Accepted`.
- **Logging & Tracing Standard Compatibility:** All logging and distributed-tracing implementation must be compatible with an established tracing standard (e.g., OpenTelemetry, or Zipkin/B3 via Micrometer's Brave bridge) rather than a bespoke scheme. Which standard to target is not yet decided — see [ADR-0004](docs/adr/0004-logging-and-tracing-standard.md). Do not hard-code a specific tracer bridge or exporter until ADR-0004 is `Accepted`. This convention is independent of that open decision:
  - **Blocking vs. Non-Blocking Error Logging:** Every logged error must state explicitly, in the log message text itself, whether it is **BLOCKING** (the current operation cannot proceed/halts as a result) or **NON-BLOCKING** (a soft/recoverable issue that processing continues past). Match the log level to the classification: **WARN** for non-blocking/soft errors, **ERROR** reserved for blocking failures. Don't rely on log level alone to convey this — state it in the message so it's unambiguous when scanning logs.

## AI Agent Collaboration Rules
- **Never Assume — Always Ask:** If any requirement, task detail, or design decision is unclear, ambiguous, or underspecified, ask the user explicitly rather than guessing or silently picking a default.
- **Architectural Vigilance:** Proactively flag any implementation detail, existing code, or proposed change — whether it's yours or the user's idea — that violates the architectural principles established here or in `SPEC.md` (Hexagonal layering, Modular Monolith, module isolation, TDD, etc.), even if not explicitly asked to review for it.
- **Security Vigilance:** Proactively flag security issues or practices that violate secure coding standards (e.g., OWASP Top 10, credential/secret handling, injection risks) whenever encountered, regardless of whether a security review was requested.
- **State Consequences:** When presenting a decision, recommendation, or trade-off, explicitly state its consequences (what becomes easier/harder, risks introduced, follow-up work created) rather than presenting it as consequence-free.
- **Shift Left:** Push architecture and security evaluation as early as possible — don't defer it to a final hardening pass. Concretely: (1) before starting implementation of a `PLAN.md` step or phase, evaluate the planned approach against the architectural principles above and check for security implications (new attack surface, secrets/credential handling, injection risks, auth/authz boundaries), and raise concerns before writing code; (2) after the code is written, evaluate it again as a check — this complements, not replaces, Architectural/Security Vigilance above; (3) `PLAN.md` Phase 15 (E2E & Hardening) is a final, cross-cutting pass, not the only point at which evaluation happens — every earlier slice/phase gets its own.

## Frontend Development Guidelines (`frontend/`)
- **Frontend Architecture Best Practices:** Follow established React/TypeScript architecture conventions — clear component/container separation, typed API client layer, colocated state near where it's used, accessibility (a11y) basics (semantic HTML, keyboard navigation, ARIA where native semantics aren't enough), and responsive design. The same "Shift Left" and "Architectural/Security Vigilance" rules above apply to `frontend/`, not just Edge/Cloud.
- **Frontend Security Best Practices:** Treat the frontend as a real attack surface — avoid XSS (no unsanitized `dangerouslySetInnerHTML`, escape/validate all user-rendered content), store auth tokens per current security best practice (not casually in `localStorage` if avoidable — this interacts with the still-open [ADR-0001](docs/adr/0001-authentication-and-authorization-approach.md) auth mechanism decision), validate/sanitize on the client as a UX convenience only (never as the sole defense — the backend must independently validate everything per the Hexagonal Architecture rules above), and avoid leaking sensitive data (config, stack traces, internal IDs) into client-visible responses or console logs.
- **Use a UX Design Agent/Skill for UX/UI Work:** For UX/UI design tasks — mockups, wireframes, screen flows, layout decisions for new pages/components (`PLAN.md` Phase 14) — use a dedicated UX design tool/skill (e.g., this environment's `design` skill) to produce and iterate on the design, rather than deciding layout purely ad hoc while writing component code.

## Git Workflow & Pull Requests (Strict Rules)
- **NEVER** commit or push directly to the `main` or `master` branch.
- Before starting any new task, feature, or phase from `PLAN.md`, always create and checkout a new branch from `main`.
- **Strict Branch Naming Convention:** The branch name MUST start with the task type (`feature/`, `chore/`, `fix/`, `refactor/`), followed immediately by the exact phase and step number from `PLAN.md`, and a short description.
- Format: `<type>/<phase>.<step>-<description>`
- Examples based on PLAN.md: `chore/0.1-gradle-skeleton`, `feature/1.2-product-state-machine`, `feature/2.1-operation-flow`.
- When the code for the task is ready and tests pass, commit using Conventional Commits containing the task number (e.g., `feat(1.2): implement product state machine`).
- Push the branch to the remote repository: `git push -u origin <branch-name>`.
- After pushing, use the GitHub CLI to create a Pull Request: `gh pr create --title "<PR Title>" --body "<PR Description>"`. If GitHub CLI is not available, provide the user with the exact GitHub web link to open the PR.
